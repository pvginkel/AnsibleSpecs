## Q1 — The four apps' Jenkinsfile and suite runner are now generated by ModernAppTemplate's root template, which no phase touches (operator-decidable, blocking)

**Problem.** P5–P8 edit each app's `Jenkinsfile` and `tools/suite_runner/local.py` directly, and
P9 edits ModernAppFrontendTemplate. As of today these files are no longer app-owned. They are
generated by a third template, ModernAppTemplate's root template, and no phase touches it. It is
not in the plan, not in `.kubecoder/config.yaml`, and not on GitHub.

**Evidence.**
- Each of the four apps committed "Adopt the root template v0.1.0" on 2026-09-26, 12:43–12:57
  (ZigbeeControl `1ac04aa`). The commit message says: "The root layer (Jenkinsfile, suite
  runner, dev stack) is now generated from ModernAppTemplate's root template … copier update at
  the repo root keeps it in sync from here on."
- Each app's root `.copier-answers.yml` at origin/main has `_src_path: ../ModernAppTemplate`,
  `_commit: v0.1.1`.
- Copier regenerated the Jenkinsfile during adoption, and the only diff was one stage rename. So
  the root template itself emits
  `registry:5000/modern-app-dev-playwright:playwright-${playwrightVersion}`. The four apps'
  origin/main Jenkinsfiles all still carry that line.
- The follow-up "Update to root template v0.1.1" rewrote `tools/suite_runner/local.py` again.
  The four runners at origin/main are now byte-identical except for `APP_NAME`, and each carries
  the "validation base image pre-bakes" comment at `:235`.
- GitHub's `pvginkel/ModernAppTemplate` `main` is `5bf46b7` (2026-09-06). It has no `copier.yml`
  and no tags, so root template v0.1.x exists only in the lane that ran the adoption.
- The same is true of the frontend template. The apps pin frontend `v0.20.1`, but GitHub's
  ModernAppFrontendTemplate stops at tag `v0.19.1`, with `main` at `861a9f1` from 2026-06-05.
  That `861a9f1` is the commit P9 is grounded on.
- The plan's grounding cites the app repos at commits from before the adoption (`33b41f9`,
  `b8a1fa7`, `96c7bb1`, `f667194`). origin/main has moved to `c979f6f`, `96927c3`, `fcb06a9`
  and `6b2f17d`. P7's claim that ElectronicsInventory's runner "has its own shape and comment
  (`local.py:8,234`)" is no longer true.

**Impact.**
- V07 fails as planned. Under the settled reading, the root template counts as a live scaffold
  that references the image.
- The next `copier update` at an app's root puts the old image line and comment back into the
  files P5–P8 changed. After D3's deletion, that app's next validation run is red.
- P9 edits a repo state that the other lane has already moved past. Pushing it in the test phase
  collides with that lane's unpushed history.
- Only the operator knows where the root template lives, when that lane lands, and whether this
  slice reaches into it (F1 covers when the run happens, not which repos it has to change). So
  it cannot be settled in a writer pass.

## Q2 — D1 brings back the setup the Playwright image was built to fix, and the planned proof doesn't check for that failure (operator-decidable)

**Problem.** D1 was ruled on two unverified premises: the Job reaches Playwright's download
host, and the frontends work on Node 24. P5 and V04 prove exactly those two. But there is a
recorded history: modern-app-dev-playwright was introduced to fix a failure of this exact
setup, where Chromium is downloaded at test time on the plain modern-app-dev base. Neither the
refinement page nor the plan mentions it.

**Evidence.** `pvginkel/ModernAppTemplate` `changelog.md`, "2026-06-05 — Frontend v0.19.0":
"This fixes validation jobs hanging after `playwright install` downloaded Chromium on the plain
`modern-app-dev` base image. The Job runs as `runAsUser: 1000` so the prebaked browser cache
(owned by `ubuntu`) is found". The entry records no root cause.

One fact points the other way. Today's suite runner caps the browser install at `timeout=900`
(`tools/suite_runner/local.py:239` at origin/main). The old entrypoint script had no cap, so a
recurrence would now show up as a red step rather than a stuck Job.

**Impact.**
- The operator agreed to D1 without seeing this failure history. D1's "If this is wrong" gives
  only "slower or flaky validation runs".
- P6–P8 go ahead on the strength of one green ZigbeeControl build. An intermittent recurrence
  may not show up in that one build.
- If it shows up later, the registry repos (D3) are already gone, and the fallback is out of
  scope.

## A1 — Pushes inside each phase, before review, aren't covered by the push rules (advisory)

**Problem.** P1–P8 have the code-writer push its repo's `main` inside the phase, before review
(Ordering constraints). The run loop leaves pushing to the test phase (`run-loop.md`, "The push
check"). The operator's global `CLAUDE.md` says: "Always get confirmation before pushing
yourself. Re-ask on every push unless the operator overrides this explicitly."

The operator did agree that each consumer is "pushed and proven" (settled list) and that D1's
first app proves on a real build. Neither of those says the executor pushes unconfirmed, before
review.

**Evidence.**
- The plan's Ordering constraints: "The push comes before the phase's review, so a review
  finding is fixed forward".
- P1: "Pushed (Ordering constraints); `kc project test` green." It does not say which comes
  first.
- Every pipeline in the estate loads JenkinsPipelineUtils unpinned from `main`
  (`KubeCoder/Jenkinsfile:1`).

**Impact.**
- A headless code-writer gets two conflicting instructions: the phase text says push, its
  standing rule says ask first. It either pauses with a `question` in each of P1–P8 or pushes
  without the confirmation the rule asks for.
- Unreviewed code reaches the shared library's `main`, seven apps' dev deploys, and one provider
  publish.
