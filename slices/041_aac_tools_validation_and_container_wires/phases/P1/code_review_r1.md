## Findings

### F1 — Minor · advisory · anchor: none · confidence: high
A type error on an empty value now has an empty source scalar. For `a:` (no value, parsed as null) where a string is expected, the message becomes `a:  (parsed as null) is not of expected type string`, with a double space and nothing quoted. For an empty sequence item (`- ` under a key) it becomes ` (parsed as null) is not of expected type string`, with a leading space. Before this change both read `value null is not of expected type string` (`quoteShort`, `error-translate.ts:314-316`). Cause: the locator returns `source: ""` for an empty scalar (probe: `sourceLocator("a:\n")("/a")` → `{line:1, scalar:{source:"", key:"a"}}`), and the type translator only checks that `node.scalar` exists, not that its source is non-empty (`error-translate.ts:197-201`). A blank required string field, such as `label:`, is a plausible authoring slip. The line still points at it and "parsed as null" still names the problem, so the message is worse but not wrong.

### F2 — Minor · advisory · anchor: none · confidence: high
On a JSON body with duplicate keys, the line and the source scalar come from the first occurrence, but the validated value comes from the last. `JSON.parse` keeps the last duplicate. The locator takes the first matching pair (`source-locate.ts:36`). Probe: `sourceLocator('{"a": 1, "a": "x"}')("/a")` → `{line:1, scalar:{source:"1"}}`, while the artifact holds `a: "x"`. A type error there would read `a: 1 (parsed as string 'x')`, pairing text and a value that do not belong together. YAML bodies are not affected, because js-yaml rejects duplicate keys with a 400. No generator in the estate emits duplicate JSON keys, so this needs malformed hand-written input.
