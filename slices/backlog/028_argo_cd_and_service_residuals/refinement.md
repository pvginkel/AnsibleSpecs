# Slice 028 — refinement

## D1 — Once a Prometheus rule carries the standing alert, does Argo CD's own immediate alert stay?
**Context.** Argo CD's notifications were turned on from day one — sent to Alertmanager, at minimum on a failed sync and on a degraded app — as the replacement signal for the old deploy step that swallowed rollout failures. Today a failed sync sends an immediate critical alert to Telegram carrying Argo CD's own error text for the sync and a link to the app; a degraded app sends a warning. Both auto-resolve after Alertmanager's five-minute default, and the Telegram receivers send resolved messages, so five minutes after a failure you get a "resolved" while the app is still broken. A still-firing alert repeats every twelve hours.
**The ask.** The card asks for a standing alert: one that stays up as long as the app is failed or degraded and resolves only when it recovers. You left the mechanism to the planner.
**Background.** The card's first option — give the alert an end time far ahead — does not exist: Argo CD's Alertmanager notifier sends labels, annotations, a link and a start time it sets itself, and there is no end-time field to template. The only route to a standing alert is a Prometheus rule over Argo CD's application metrics. Argo CD exposes no metrics today, so the slice turns the controller's metrics on and adds a scrape and the rules in the Prometheus deploy repo. What is left to choose is what becomes of the immediate notification once the rule exists.
**Why yours.** It changes what reaches you on Telegram for every failed sync, and it amends a decision you made.
**Recommendation.** Keep the immediate alert as the event and silence its false "resolved" (it goes to a Telegram receiver that sends no resolve); add Prometheus rules for the standing state — an app still out of sync, or still degraded, some minutes after the failure (past Argo CD's own sync retries, about four minutes) fires and stays up until the app recovers, then resolves for real. The decision that turned notifications on stands, amended to say the notification is the event and the rule is the state. Trade-off: two messages per failure — the immediate one with the error text, then the standing one some minutes later.
**The other way.** Let the rules replace the notification path entirely: one alert per failure with a true resolve, but it arrives a few minutes later, names only the app and its state (the error text is one click away in Argo CD), and retires the notification path that decision established.
**If this is wrong.** An extra or a missing Telegram message per failed sync; either is reversible in one small change.

## D2 — Close the provider-download item as already covered by Argo CD's sync retry?
**Context.** The card was filed against the old HelmCharts deploy path, where one failed provider download took a whole deploy down. At triage the session advised keeping it for the Argo CD side — every sync runs the pre-sync hook's Terraform init from a fresh clone — and you agreed. Measured earlier and carried on the card: a committed lock file without an already-warm provider cache still downloads the checksums, and a warm cache means persistence, which you ruled out on the host where Jenkins runs Terraform; so only a retry or a mirror removes the failure.
**The ask.** Stop a transient failure downloading a Terraform provider during an app's pre-sync hook from failing the deploy.
**Background.** Measured live over about 48 hours: the hook ran 472 times (roughly 237 syncs a day) and failed twice — the same app, the same public provider, a server error from the download host. Argo CD's sync retry (three retries, thirty seconds doubling) re-ran the hook and the sync succeeded three to four minutes later with nobody involved. Every auto-synced app carries that retry; apps without auto-sync are synced by hand. The shared hook chart states the design outright: retries belong to the sync policy, not the hook job. The card's felt harm does not hold on Argo CD; what remains is a failed job record and a few minutes' delay. The complaint as filed is closed by what already exists.
**Why yours.** It drops a requirement you agreed to keep at triage.
**Recommendation.** Close the item as not needed; no hook change. Trade-off: a download outage longer than the retry window (about four minutes) still leaves that app's sync failed until the next commit or a manual sync — and with the standing alert from D1 in place, that is a standing alert rather than a five-minute one.
**The other way.** Route the public providers through the homelab provider mirror the hook already uses for the homelab provider, taking the public download host out of the path entirely (the card's own deferred item). Cost: populating the mirror with the five public providers (how is not verified), a hook image change, and that image reaching the apps through the shared chart that pins it — two or three more phases.
**If this is wrong.** An occasional sync that fails for good during a long outage at the download host, caught by the standing alert and fixed by re-syncing.

## D3 — Who pushes the four deploy repos: the run, or you afterwards?
**Context.** A push to a deploy repo's main is a production deploy with nobody pressing a key, and this repo's rule is that such actions are yours. The migration's push authority was for the bulk migration only; the slices before it held every push that deploys and left it to you.
**The ask.** Four deploy repos change in this slice and go live only when their main is pushed; the question is whether the run pushes them or you do.
**Background.** What each push does. The Argo CD deploy repo: Argo CD reconfigures itself — the controller restarts to expose metrics, and the login fix changes its config. The Prometheus deploy repo: the new scrape, rules and alert routing load. The git-sync deploy repo: gitblit restarts with the new init container, so search and the MCP server are briefly down. The KubeCoder deploy repo: only the promotion job's script changes, which takes effect when someone runs the job (not verified: whether a push to its main also re-syncs KubeCoder's dev stage). Every live check the slice owes — logging in through the short hostname, the standing alert firing and resolving, gitblit's bookkeeping file pruned at start, a promotion re-run finishing a tagless release — can only run after the push.
**Why yours.** Four production deploys you did not press, or a slice that closes with its live checks on your list.
**Recommendation.** Hold all four; the run builds, renders and checks everything it can offline, and the live checks are owed until you push. Trade-off: the slice closes with live checks outstanding on your list.
**The other way.** The run pushes each repo itself and verifies live, one at a time — the slice closes proven, at the cost of four production deploys you did not press.
**If this is wrong.** Either a slice with owed checks, or deploys you would rather have timed yourself.
