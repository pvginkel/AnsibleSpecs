# Slice 033 — refinement

## D1 — The library's behaviour tests run in the pre-push Maven gate; no Jenkins job is added for the library
**Context.** Every Jenkins job in the estate (104 consumers) loads the shared library JenkinsPipelineUtils unpinned from main, so a broken push breaks the next build of all of them. An earlier slice gave the library a pre-push compile gate: on every project test run, each function file is compiled through the controller's own pipeline transform. The review accepted a self-test for the library; its docs half went to the later style guide, its test half is this slice's.
**The ask.** The review proposed a Jenkinsfile in the library repo plus a push-triggered Jenkins job that loads the library at the pushed commit and asserts its pure functions: the pin apply and replace, the YAML plain-safe check, the tracking-tag resolver, the notification escaper, the change-set check. The refresh asked whether that job is needed or the pre-push test run is enough, and the slice left it to this session.
**Background.** The existing Maven harness can call the library's functions directly; one of them, the tracking-tag resolver, has had behaviour tests there since 2026-09-29. A prototype in a throwaway copy passed the escaper and the pin-replace in about ten lines each; the pin-apply and plain-safe functions are pure and non-CPS the same way, and the change-set check becomes callable once it gets the non-CPS annotation this slice adds (true and false cases passed against a fake build object). No new dependency; the third-party pipeline-unit framework is out, as it conflicts with the pinned Groovy. What a job would add is real runtime: step signatures, serialization errors, a step called from a non-CPS method, pod and filesystem permissions. But it runs after the push, so it cannot keep a broken main from the consumers. The failure the review cites, a KubeCoder build denied access in a file write, was a pod-permission bug no offline test could catch, and a job would have caught it only after the push. A job costs a Jenkinsfile in the library, a job created through the API, and a pod per run.
**Why yours.** The review proposed the job, and you may want the runtime smoke regardless of when it runs.
**Recommendation.** The pre-push Maven tests only, on every project test run; no Jenkins job. Trade-off: runtime-only bugs, permissions and serialization, stay uncaught until a consumer's build, exactly as today.
**The other way.** Add the post-push job as well: a job plus a pod per library push, catching runtime bugs only after main already carries them.
**If this is wrong.** A runtime-class library bug still surfaces in a consumer build, which is the status quo; the job can be added later on its own.
**Operator.** "D1 is fine."

## D2 — The run pushes the library itself; KubeCoder's converted Jenkinsfile is held for your Replay and your push
**Context.** The standing rules say each push needs your OK and each Replay needs your OK. Your step order for the trial is: convert KubeCoder's Build-Main Jenkinsfile to declarative, you replay Build-Main with the converted script (a real build and, through the pin commit, an Argo rollout to dev), then push. The library floats on main for all 104 consumers, so a library push is live estate-wide at once, with nothing to roll back but a revert.
**The ask.** The slice changes two repos. In the library: the gate's version-pin bump, the behaviour tests, the non-CPS annotation on the change-set check, the dead-code deletions, and the new pod-YAML helper the declarative conversion is built on. In KubeCoder: the converted Jenkinsfile. Each needs a push, and the order has to work.
**Background.** A Replay swaps only the Jenkinsfile; the library still comes from main, so the pod-YAML helper must be on the library's main before your Replay can run at all. Every library change passes the compile-plus-behaviour gate before it goes, and the deletions remove code with no caller anywhere in the estate. Verifying the change-set annotation also needs the library on main, followed by the next build of one of its two callers, the DockerImages build or the Ansible iac-image build.
**Why yours.** It is a procedure you run and a risk you carry: the library push goes live for every job.
**Recommendation.** The run's driver pushes JenkinsPipelineUtils at the end of the run, once the gates pass; starting the run is your OK for that one push. KubeCoder is held: the run commits the converted Jenkinsfile and does not push it, and you replay Build-Main and push by hand. Trade-off: the library goes live estate-wide without a separate click, trusting the gate.
**The other way.** Hold both: you push the library by hand, then replay, then push KubeCoder. One more manual push, and the run cannot confirm the library landed.
**If this is wrong.** A library regression that got past the gate breaks consumer builds until it is reverted.
**Operator.** "But even the removing dead code stuff has a limited risk. We'll see red pipelines quickly enough, and the revert is trivial. I was worried you were gutting the thing, but nothing of the kind. In that case, by al means, just push to main."

## D3 — The converted Jenkinsfile gets no when block and no post block, because the scripted file has nothing they would express
**Context.** The plan is drafted in four phases — the library's gate at the controller's version with behaviour tests, the change-set check going non-CPS with the dead helpers removed, a library helper that renders the pod as YAML for a declarative agent, and KubeCoder's Build-Main Jenkinsfile converted — and your round-one rulings stand: tests in the pre-push Maven gate and no library job; the run pushes the library and KubeCoder is held for your Replay and push; the KubeCoder gate is the controller's full declarative linter check. The trial wording you adopted lists the converted file's shape as an agent from YAML built by a library helper, options and triggers for its job config, a when block and a post block, and the acceptance criterion carries that word for word.
**The ask.** Convert KubeCoder's Build-Main Jenkinsfile to declarative without changing what the build does. As the criterion stands, the trial cannot pass unless the converted file gains both a when block and a post block.
**Background.** The scripted file has no conditional stage and no failure or cleanup handling: every stage runs on every build, and there is no branch, no try, no catch and no finally anywhere in it. The review named when and post as what declarative buys in general — a conditional stage instead of the skip-marker hack, post handlers — not as something this file needs.
**Why yours.** The two constructs are in your own adopted wording, and dropping them rewords an acceptance criterion.
**Recommendation.** Convert faithfully: the file gets neither block, and the criterion drops those two words. Trade-off: the trial never shows those two constructs in use, so your verdict on declarative is judged on agent, options, triggers and stages only. The estate's real conditional-stage case is the Ansible iac-image pipeline's stage-skip marker — a pod pipeline that a "migrate all" slice converts anyway.
**The other way.** Add a real use of each so the trial shows them: it changes what the build does, there is no credible conditional stage (every image stage feeds the pin write, so skipping one would pin an image never built), and the only post candidate is a failure alert the Jenkins Telegram bot already sends on any failure.
**If this is wrong.** You judge declarative without having seen when or post; the iac-image case shows the former, or you ask for one more file converted.
**Operator.** "Agree"
