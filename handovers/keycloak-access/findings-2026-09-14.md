# Keycloak access and hardening — findings, 2026-09-14

Read-only investigation, done during slice 018's refinement after the operator asked "do an
investigation of Keycloak and see what still needs to be done to harden that", open "to both
hardening the configuration and creating a separate realm". Nothing was changed.

**Method and limits.** Admin REST API with the IoT app's `iotsupport-admin` service account
(OpenBao `eso/prd/iot/prd/keycloak-admin`, borrowed with operator permission, read through its
ESO-materialised Secret; the temporary files were deleted). That account holds only
`realm-management: manage-clients` on `homelab`, so clients and client scopes were readable;
users, groups, role mappings, the full realm settings, authentication flows, events, identity
providers, the `master` realm and the dev Keycloak were **not**. Also: HelmCharts/DockerImages/
Ansible config, Jenkins `config.xml` (authorization block only), anonymous login-page probes, and
upstream Keycloak security advisories. Internet reachability could not be tested from the pod (no
hairpin route to the public IP).

## Act now

1. **Any `homelab`-realm account is a full Jenkins admin.** `jenkins.webathome.org` is public;
   the security realm is OpenID Connect and the authorization strategy is
   `FullControlOnceLoggedInAuthorizationStrategy` (anonymous read denied). The Keycloak `jenkins`
   client has no roles and nothing else gates the login. Fix (operator, Manage Jenkins → Security →
   Authorization): Matrix-based security with only the operator's user holding Overall/Administer.
2. **Keycloak 26.5.1 (released 2026-01-14) serves the public `auth.ginbov.nl`; the latest is
   26.7.3 (2026-08-31).** High-severity advisories patched since include CVE-2026-11800
   (authentication bypass via JWT algorithm confusion, fixed 26.6.4), CVE-2026-9795 (privilege
   escalation via scope-mapping enforcement, 26.6.4), CVE-2026-9099 (group-admin → realm-admin,
   26.6.4), CVE-2026-9800 and CVE-2026-15573 (authorization bypass via URI comparison, 26.6.4 /
   26.7.1), CVE-2026-2092 (encrypted SAML assertions, 26.5.5). Image:
   `registry:5000/keycloak:26.5.1-postgres-health-ispn` (HelmCharts `charts/keycloak/values.yaml`,
   a DockerImages build).
3. **The chart hardcodes the bootstrap admin as `admin` / `admin`**
   (`charts/keycloak/templates/keycloak-deployment.yaml`, `KC_BOOTSTRAP_ADMIN_*`). Keycloak uses it
   only to create a temporary `master`-realm admin when none exists — but if that account was never
   replaced, the `master` realm, whose login page and admin console answer on the public hostname,
   has a known password. **Not checked**: it needs a `master`-realm read or a login attempt (which
   would return an admin token).

## Keycloak configuration

- Brute-force protection reads `false` on `homelab` (from the reduced realm view the account gets) —
  likely off, on a public login page.
- No registration, forgot-password or remember-me link on the `homelab`, `master` or `homelab-dev`
  login pages.
- The `master` realm's login and admin console are served on the public hostname. The front door's
  `is-public` is per host, and nginx-configurator has no per-path annotation (its keys: server-name,
  service-namespace, service-name, target, target-port, is-public, enable-ssl, base, keep-alive,
  frame-options), so `/admin` and `/realms/master` cannot be kept LAN-only without a configurator
  change.
- `KC_HOSTNAME_STRICT=false`, `KC_PROXY_HEADERS=xforwarded`, HTTP enabled behind the proxy — the
  chart's comments are Keycloak's quick-start text ("In this explorative setup…").
- `iotsupport-admin` — the service account of a public app — holds realm-wide `manage-clients`: a
  compromise of IoT Support can rewrite any client, e.g. the `jenkins` or `openbao` client's
  redirect URIs. It and `iotsupport-pipeline` also carry redirect/web-origin `/*`.
- Direct access grants (the password grant, which bypasses the login page) are on for `iotsupport`
  and `open-webui`.
- Guacamole uses a public client with the implicit flow (tokens in the URL fragment).
- The default `roles` scope puts client roles in the access token only; `fullScopeAllowed` is on for
  nearly every client, so tokens carry all of a user's roles.
- Not inspected: users, groups, role mappings, required actions and OTP policy, password policy,
  events, sessions, the `master` realm, the dev Keycloak.

## The access-model question

The operator wants Grafana, Prometheus, Jenkins, Kubernetes (Headlamp) "and maybe more" kept away
from non-infrastructure accounts. Two shapes, both of which still need the hardening above:

- **A. One realm, a Keycloak-side gate.** Each infrastructure client gets an access role and a
  browser-flow override that denies users without it ("Condition – user role" + "Deny access",
  placed so it also runs on an existing SSO session). It works for apps that cannot check roles
  themselves (Jenkins, Guacamole, Argo CD, Prometheus) with one account and one sign-in. Not tested
  here.
- **B. A separate infrastructure realm.** Realm membership is the gate. It costs a second account
  and sign-in, a matching dev realm, and moving the existing infrastructure clients (`jenkins`,
  `argocd`, `guacamole`, `openbao`, and whichever of DHCP / Zigbee / IoT count) with their app
  configuration; keycloak-tf (#68) then models two realms.
