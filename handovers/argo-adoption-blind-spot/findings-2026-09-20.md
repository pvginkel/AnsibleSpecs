# What an Argo CD cutover cannot change — findings, 2026-09-20

Read-only investigation during slice 010's close-out (entry S11), after the operator asked
whether the `imagePullPolicy` finding might have other occurrences. Nothing in the estate was
changed; the only writes were a throwaway ConfigMap in prd's `development` namespace, deleted
after the probe.

**The question.** Slice 010 drops `imagePullPolicy: Always` from KubeCoderDeploy's five pinned
Deployments, and slice 012 expects that drop to go live at the cutover. It does not. The general
form: *when Argo CD adopts a release Helm created, which of the old chart's settings does its
first sync fail to remove?*

## The mechanism, proven

Argo does diff against the live object — that is one input. It needs a third to tell "a field I
used to declare and have now dropped" from "a field the API server defaulted or another
controller owns". Client-side apply, Argo's default, uses the
`kubectl.kubernetes.io/last-applied-configuration` annotation for that. Helm-created objects have
none (Helm 4.3 applies server-side and writes no such annotation), so Argo falls back to a
two-way diff in which "what I declared last time" equals "what I declare now" — the delete bucket
is empty by construction.

Probed with a ConfigMap in `development`, manager `helm` (SSA) creating `helmonly` + `keep`, then
manager `argocd-controller` applying `keep` alone:

| Attempt | `helmonly` removed? |
| --- | --- |
| `argocd-controller` applies client-side without it | **no** |
| `argocd-controller` applies `--server-side --force-conflicts` without it | **no** — helm still owns it |
| helm's `managedFields` entry deleted, then SSA re-applied | **no**, twice: stripping ownership does not touch the value, and an unowned field has no owner to prune it |
| `argocd-controller` *declares* the field, then drops it in a later apply | **yes** |

Two consequences worth keeping:

1. **Server-side apply does not fix an adoption.** SSA deletes a field when the manager that owns
   it stops declaring it; a *different* manager applying without the field leaves it alone. At a
   cutover the field is owned by `helm`, not by Argo.
2. **It is a one-time artifact, not a standing defect.** Argo's first client-side apply writes
   `last-applied-configuration` itself (kubectl warns that it is doing so). From then on
   three-way merge works and later chart removals take effect normally. Only fields the old chart
   set *and* the new render never mentions stay frozen, at their Helm values, indefinitely.

## The test, and the whole inventory

The rule is decidable: **a field sticks iff `metadata.managedFields` says `helm` owns it and the
Argo render never declares it.** One level up: a Helm-stamped object the render does not contain
is never adopted and never pruned. `stuck_fields.py` in this folder computes both from
`helm template` output and `kubectl get --show-managed-fields`. Run against KubeCoderDeploy
`80d96bb`'s render and the live releases on 2026-09-20:

| | `kubecoder-dev` | `kubecoder-prd` |
| --- | --- | --- |
| Helm-stamped live objects | 30 | 31 |
| Objects in the render | 24 | 25 |
| `metadata.labels` stuck | 22 | 23 |
| `metadata.annotations` stuck | 21+2 | 21+4 |
| `imagePullPolicy` stuck | 5 | 5 |
| `spec.template.metadata.annotations` stuck | 2 | 2 |
| **total stuck fields** | **52** | **55** |

**Objects: nothing is stranded.** The eight Secrets the check flags per stage
(`kubecoder-github-token`, `kubecoder-secret-catalog`, …) are ESO output — `ownerReferences` to
an `ExternalSecret`, the external-secrets controller their only field manager — and they carry a
Helm stamp only because ESO copies it from the CR. The render carries all eight ExternalSecrets
that produce them.

**Fields: three things, two already known.**

- `imagePullPolicy` on the five pinned containers — slice 010 close-out S11.
- `spec.template.metadata.annotations` on `kubecoder-bot` and `kubecoder-mcp`, the stale
  deployment timestamp — same entry; static, rolls nothing.
- `metadata.labels` and `metadata.annotations` on every adopted object: the chart renders neither,
  so `app.kubernetes.io/managed-by: Helm` and `meta.helm.sh/release-name` / `-namespace` survive
  the cutover permanently. Inert in themselves, but anything keyed on them keeps counting a
  migrated app as Helm-managed — which is the premise HelmCharts' `audit-prd-orphans` reasons
  from (HC-12). Declaring the labels in the chart takes ownership and overwrites them.

No third surprise: beyond what slice 012 already tracks, the entire residue is Helm's own
provenance stamps.

## What this leaves open

- **The mechanism for KubeCoder** is slice 012's: declare `imagePullPolicy` explicitly in the
  chart, which works under either apply mode, and write D145's update from what is then live.
- **The check belongs in the toolchain.** As a pre-flight before each cutover it produces the
  table above in one command, for any of the 45 releases, instead of a review finding one instance
  by hand. `stuck_fields.py` here is the working copy, not a supported tool; ArgoCDTools is the
  home, with the argocd runbook pointing at it.
- **The migration mode is undecided.** Adopt in place, and every cutover must enumerate what the
  old chart set and the new one does not; or recreate — delete the namespace and let Argo build
  it — which needs no enumeration at all but only suits a stage with no live state to interrupt.
  `kubecoder-dev` holds three control-plane Deployments and nothing else; `kubecoder-prd` also
  holds the running environment pods. Both PVs are `Retain` over `/zpool5/kubecoder`, so `/work`
  survives a namespace delete, but the PVC delete leaves the PV `Released` with a stale
  `claimRef`, and slice 012's Terraform state surgery is owed either way. This belongs in
  `argo-cd/decisions.md`.

## Caveat

The figures are the render from `main` on 2026-09-20. Slice 012's requirement 5 re-syncs the
chart from HelmCharts before the cutover, so re-run the check then rather than trusting this
table — which is the argument for keeping it as a script.
